# 架構決策：為什麼是這樣分層

這份是對外說明用的架構敘述。每個結論都附「在程式裡怎麼驗證」，
講不出驗證方式的不寫。

紀錄日期 2026-09-12。

---

## 一、要解的是一個權衡問題

地政局對這類系統有兩個同時成立的要求。

**確定性與證據性。** 徵收案會被訴願。同一個案子問兩次必須得到一樣的答案，
而且每個數字都要說得出法源，指得回官方評價基準明細表的哪一頁哪一格。
算錯會影響補償金額，責任歸屬必須清楚。

**個案變動性。** 用地類別不同（商業、住宅、農業、工業）判準就不同，
行政區不同基準表就不同，法規會修，報表格式會改版，
而且勘查資料的來源格式各式各樣。

這兩個要求的極端解都不能用。

硬編碼有最好的確定性，換一個個案就失效，維護成本會隨案件類型線性成長。

生成式模型有最好的適應性，但失去確定性。同一份輸入兩次可能得到不同答案，
說不出為什麼判這一級，而在會被訴願的案子上那等於沒有答案。
這不是技術取捨的問題，是責任歸屬的問題。

所以選的是模組化分層：把「會變的東西」與「不該變的東西」拆開，
讓每一種變動只需要動一層，其餘不動。確定性由「同一份輸入加同一組規則
永遠得到同一份結果」提供，彈性由「換掉那一層」提供。

## 二、四層與各層的變動成本

| 層 | 什麼時候要動 | 動什麼 | 成本 |
| --- | --- | --- | --- |
| 輸入 | 換檔案格式、換表格排版 | `parser/`（PDF）或 `xlsxform/read.py`（xlsx） | 中，而且這層最脆弱 |
| 規則 | 換行政區、換用地類別 | `kernel/rules/*.json` | 最低，不動程式碼 |
| 核心 | 法規修條文 | `kernel/src/` | 最高，但有 Golden Case 守著 |
| 輸出 | 報表改版、要新的檔案格式 | `xlsxform/layout.py` 或 `pdfform/` | 低，不碰計算 |

把成本差異講清楚比說「模組化」有說服力。三種變動裡最常發生的（換行政區）
成本最低，最少發生的（法規修改）成本最高，而且那時有測試逐格擋著。

### 輸入層最脆弱，所以要講

這層是唯一會因為外部因素自己壞掉的部分。PDF 版面改了座標就失效，
而我們無法控制別人的排版。

目前有兩個實作，走不同策略。`parser/` 吃 PDF，靠座標比對，綁版面。
`xlsxform/read.py` 吃 xlsx，靠格位對映，結構化程度高得多。
正式題目的勘查表是 xlsx，所以主線走後者。

下一步是接 Amazon Textract 處理掃描件與版面變動，但辨識結果必須先攤給人
確認再進計算，不能直接餵給規則引擎。理由見第四節。

### 規則層是整個設計的重點

29 個修正細項的判級級距與 5×5 修正矩陣全部是 JSON 資料，不是程式碼。
換一個行政區或用地類別是編一份新的 JSON。

每份規則集帶著自己的身分：

```json
"scope": {"district": "新北市樹林區", "land_use": "普通住宅用地", "factor_kind": "regional"}
```

**怎麼驗證**：`python scripts/demo-review.py` 第三段。同一份輸入換一組規則集
（金山商業換成樹林住宅），結果跟著變，程式碼一行沒改。

### 核心層有 Golden Case 守著

判級、矩陣查表、群組小計、總修正數、絕對值加總、權重、加權平均、
第 21 條分段進位，全部在 `kernel/`。它不 import 任何其他模組。

**怎麼驗證**：`grep -r "^from\|^import" kernel/` 看不到任何專案內的模組。
以及 `kernel/tests/` 的 181 個測試，其中金山商業用地案能逐格重現官方答案。

### 輸出層有兩個實作，這是最強的證據

`xlsxform/` 回填官方 xlsx 範本，`pdfform/` 回填官方 PDF 書表。
兩套完全不同的輸出共用同一個 `kernel`。

`xlsxform/layout.py` 整份只有一個函式，而那個函式是自檢，其餘全是座標常數。
報表改版是改那份常數表，不動計算。

**怎麼驗證**：`grep -cE "^def |^class " xlsxform/layout.py` 得到 1。
以及 `pdfform/fill.py` 的計算函式是參數傳進來的（依賴注入），
它不知道 `kernel` 存在。

## 三、確定性的定義

確定性不等於「不准改」。它的意思是：

1. 同一份輸入加同一組規則，永遠得到同一份結果。沒有隨機性，沒有模型。
2. 每個數字都指得回來源。表5-1 的 116 格等級與 87 格修正率，
   每一格都記著現地量測值、判到第幾級、判級依據、基準表第幾頁、
   矩陣查表結果。
3. 人的每一次介入都留痕跡。容積率一律以 200% 計算是地價查估單位的指示，
   那個覆寫記在 `case_overrides`，而且會出現在計算依據工作表與備註欄裡。

第三點是關鍵。系統不禁止人工調整，系統要求人工調整必須被記錄。
禁止調整會讓系統在實務上不可用，因為個案永遠有例外。

**怎麼驗證**：產出目錄的「計算依據」工作表，114 列，
每列有判級依據與矩陣查表兩欄。容積率那幾列會寫明勘查表原載 260% 而以 200% 計算。

## 四、刻意不做的事

### 不用模型算數字

計算全程不經過生成式模型，包含計算依據工作表上的敘述文字。
敘述是規則式產生的，所以同一份輸入永遠得到同一段文字。

模型可以加在兩個位置：把勘查表 PDF 或掃描件辨識成結構化欄位，
以及把規則式敘述潤飾成更好讀的文字。兩者都在規則引擎之外，不取代它。
辨識結果必須先攤給人確認。

### 不接地圖 API 算距離

評價基準明細表的級距是「區段內有學校或距離未滿 300m」這種法定判準。
地圖 API 的距離會因為路徑演算法、資料更新、服務可用性而變動。
同一個案子今天算 280 公尺明天算 310 公尺，等級跳一級，修正率跟著變，
補償金額也變。那在會被訴願的案子上是致命的。

現在的做法是距離由勘查人員現地量測後填在勘查表上，系統只負責查表。
責任歸屬清楚，數字追溯得到勘查表那一格。

### 不宣稱準確率

這是規則引擎不是預測模型。能驗的是規則本身與官方基準表逐格一致，
那有測試可以現場跑。

## 五、擴充路徑

依成本排序，前兩項不需要改程式碼。

**加一個行政區或用地類別**：編一份規則集 JSON。目前有三份
（金山商業區域因素、金山商業個別因素、樹林住宅區域因素）。
還缺樹林住宅的個別因素那份，而官方評價基準明細表第 6 到 9 頁就是它的來源。

**加一種報表格式**：加一份座標對映表。

**加一種輸入格式**：實作一個回傳統一勘查事實結構的讀取器。
現有兩個實作可以照著寫。

**案件類型自動辨識**：規則集的 `scope` 與 `parser` 抽出的 `land_use`
已經都在，缺的是把兩者對起來的索引。設計原則見下一節。

## 六、人機分工

系統負責查表、加總、比對、留痕跡。人負責現地量測、認定用地類別、
判斷例外情形、簽署。

自動辨識的結果一律當成「建議值」而不是「答案」。畫面上要看得到系統辨識了
什麼、目前用的是什麼、兩者是否一致。人改了要留記錄，並出現在交付書表上。

找不到對應的規則集時停下來報錯，不退回預設值。
安靜使用錯的基準表比明確失敗糟得多。
