# 這個系統在做什麼

**土地徵收補償市價查估書表的自動審查工具。**

## 業務背景

政府徵收私人土地時必須發放補償金，金額由估價師依《土地徵收補償市價查估
辦法》計算，並填寫在三張官方書表上：

| 表別 | 正式名稱 | 內容 |
| --- | --- | --- |
| 表1 | 地價區段勘查表 | 現地量測值與所填的優劣等級 |
| 表5-2 | 影響地價區域因素分析明細表 | 區域因素 28 項的等級與修正率 |
| 表4 | 比較法調查估價表 | 個別因素 19 項、試算價格、比準地比較價格 |

這些表格會填錯，而且錯一格會沿著計算鏈一路影響到最終的補償金額。過去複查
必須由人拿著捲尺與法規手冊逐格核對，是最耗時也最容易漏掉的工作。

### 表格編號會隨用地類別改變（2026-09-12 補記）

上表是開發期使用的金山商業用地範本的編號。實際拿到的樹林普通住宅用地題目
換了編號與張數，`parser/detect.py` 依名稱辨識，所以這件事會直接影響辨識結果。

| | 金山商業用地（開發範本） | 樹林普通住宅用地（正式題目） |
| --- | --- | --- |
| 勘查表 | 表1，共 1 張（已填好） | 表3，共 4 張（P001 比準地 ＋ P002/P003/P004 標的） |
| 區域因素明細表 | 表5-2，28 個細項 | 表5-1，29 個細項（空白待填） |
| 比較法調查估價表 | 表4 | 表4（空白待填） |
| 群組數 | 7 個（含工商活動） | 8 個（無工商活動，多出土地改良與其他影響因素） |

住宅用地沒有「百貨公司／金融機構／娛樂設施／大型展示中心／顧客通行量／
店鋪毗連狀態」這組工商活動因素，改成「電業設施及公用氣體燃料設施」
「殯葬設施」「廢棄物處理設施」三項特殊設施，並多出「土地改良」與
「其他影響因素」兩個群組。

## 系統做的事

有兩條路，用的是同一個規則引擎，方向相反。

### 路徑一：審查已填好的書表

使用者上傳估價師填好的書表 PDF，系統：

1. 辨識出 PDF 裡的表1、表5-2、表4，抽出每一格的值與座標
2. 依官方評價基準明細表**自己重算一遍**
3. 三層逐格比對估價師填的值與重算的值，指出不符之處
4. 每個結論都附上依據鏈：量測值 → 基準表哪一列 → 矩陣哪一格 → 手冊第幾頁
5. 可將重算結果填回官方版面，輸出三張可交件的 PDF

### 路徑二：從勘查資料算出該填什麼（2026-09-12 新增）

正式題目的表5-1 與表4 是空白待填，而勘查表（表3）根本沒有優劣等級這一欄，
所以路徑一的第一層檢核在那個案子沒有對照對象。這條路是：

1. 讀勘查事實（`kernel/fixtures/*.json`，欄位標註來源頁碼）
2. `kernel.build_table5_1()` 算出表5-1 的每一格：116 格優劣等級、87 格修正
   百分比、24 格群組小計、3 格總修正數，每格帶依據字串
3. 接著算表4：區域因素調整百分率、調整百分率絕對值加總、比較標的權重、
   試算價格、比準地比較價格、比準地地價
4. `xlsxform` 回填官方 xlsx 範本並另存，一行指令跑完

命題文件的預期成果第一項寫的是「透過 AI 輔助完成估價書填寫流程」，
三個痛點之一是「修正率加總及跨表抄填（如區域因素總修正數）容易出現計算或
填載錯誤」。路徑二直接對應那件事。實測官方三份 xlsx 範本的 Excel 公式數量
分別是 0、0、1（唯一那個是印給人看的說明文字），也就是局處目前是手算的。

產出分兩種：**活版**把加總與四則運算寫成 Excel 公式（局處把個別因素填進表4 之後
下游自動更新），**定版**全部是規則引擎算好的數值（用於對照答案與轉 PDF）。
兩份的數字必須一致，那是一道交叉驗證。

細節見 `.kiro/specs/fill-shulin-forms/`。

### 三層審查對應官方審查重點

法源為《土地徵收補償市價查估作業手冊》印刷頁 11–13。

| 層 | 比對內容 | 依據 |
| --- | --- | --- |
| 第一層 | 表1 內部：量測值 vs 所填等級 | 最容易被忽略，錯在源頭會連鎖到賠償金 |
| 第二層 | 表1 → 表5-2：兩表等級須一致 | 審查重點第 vi 項 |
| 第三層 | 表5-2 → 表4：總修正數須相符 | 審查重點第 vii 項 |

官方範本目前共查 77 格。

## 核心設計主張

> **每一個數字都指得回官方文件的具體位置，沒有任何一個是模型生成的。**

這是整個專案的立場，會影響所有技術決策：

- 計算一律由 `kernel/` 的規則引擎執行，規則來自官方評價基準明細表
- 辨識出的每個欄位都記錄 provenance（頁碼、座標、原始文字）
- **API 層不做任何計算**，一旦 API 開始自己算，追溯鏈就斷了
- 查不到的項目列入 `not_checkable` 並說明原因，**不假裝通過**
- 產表時沒有值的格子留白，不回填原檔內容，這樣才分得出哪些是系統算的

`checked` 格數必須誠實回報。少查 23 項的「相符」與全查的「相符」在畫面上
不該長得一樣。

## 目前的已知限制

- 規則集有兩組區域因素（金山商業 `jinshan_commercial_regional`、樹林住宅
  `shulin_residential_regional`），個別因素只有金山商業一組
  （`jinshan_commercial_individual`）
- 樹林那組的內政部合規性尚未驗證。`kernel/rules/moi_caps_regional.json` 只編了
  附件24 的商業用地表，住宅用地那份（附件24 第1表）還沒編，而住宅用地不能套
  商業用地的上限欄位。`check_ruleset()` 會對樹林 29 項全數發 WARN，那代表
  「合規尚未驗證」而不是「不予調整」
- `api/main.py` 寫死預設規則集，上傳其他行政區的書表會用錯規則集審查而且不提示。
  表5-1 已解析出 `land_use`，但沒拿來選規則集
- 比較標的的區域因素等級沿用比準地，因為官方範本只有一張表1，跨區段案件
  需要第二張表1。這使表5-2 產出的修正率目前全為 0
- 只讀 PDF 的文字層，掃描的紙本 PDF 無法辨識
- 表6（宗地市價）尚未實作
