# 需求：匯入填好的勘查表 xlsx

> 建立於 2026-09-12。這份 spec 補上系統的入口。
> 相關：`../fill-shulin-forms/` 是輸出端（回填三份書表），這份是輸入端。

---

## 1. 要解決的問題

整條計算鏈已經通了，但入口只有一份人工核對的 JSON
（`kernel/fixtures/shulin_survey_facts.json`）。使用者不可能自己編那個檔案，
所以實務上等於沒有入口。

原本的入口是 PDF。`parser/` 靠一份人工量測的座標位置表把值挖出來，對開發用的
金山範本完整可用（逐格審查零不符、零查不動、28 個區域因素全部能從量測值反推
等級），但正式題目的表3 是雙欄、22 欄、188 個合併格，版面與金山那張完全不同，
位置表對不上。實測 6 頁只認出 1 頁，而那頁解析拋
`ValueError: 表4 表頭判讀失敗：[]`。

**這不是「辨識表格做不到」，是「辨識綁定特定版面」。** 描述系統能力時這兩者
不可混用。

## 2. 為什麼選 xlsx 而不是先修 PDF

| | xlsx | PDF（座標） | 圖片／掃描件（OCR） |
| --- | --- | --- | --- |
| 資料形態 | 結構化，格子有座標也有值 | 只有「某位置有某串文字」 | 只有像素 |
| 換版面的成本 | 重新量格位對映 | 重新量座標位置表 | 不必改（服務自己認） |
| 錯誤模式 | 讀不到就是空的 | 對不上就明確報錯 | **可能看起來成功但認錯** |
| 本專案現況 | 格位對映已有且雙向可用 | 位置表綁金山版面 | 完全沒有 |

三個理由選 xlsx：

1. **成本最低。** `xlsxform/layout.py` 那份格位對映是為了寫入而量的，實測反向
   讀取也可行（29 個細項的等級與修正率、表3 的欄位值都讀得出來）。
2. **最可靠。** 格子裡有什麼就是什麼，不會猜錯。OCR 是三者中唯一會安靜給出錯誤
   結果的，那違反專案紅線的精神（查不到就說查不到，不假裝通過）。
3. **貼近實務。** 局處手上本來就有那三份 xlsx 範本，日常工作很可能就是在 Excel
   裡填。要求他們印成 PDF 再上傳反而多一步。

PDF 與圖片列為後續工作。PDF 的下一步不是重測座標（投入最大、泛用性最差、
換一次用地類別就要重做），而是改用 Amazon Textract（在競賽白名單內、換版面不必
改程式碼、同時是生成式 AI 應用的正當位置）。但 Textract 的辨識結果必須先攤給人
確認再進計算，不能直接算下去。

## 3. 輸入

**填好的表3 勘查表 xlsx**，一個工作表一個地價區段。

工作表的辨識方式：名稱含區段編號（`P001-00` 這種格式）。`xlsxform` 產出的檔案
命名為 `表3 P001-00`，官方空白範本只有一張叫「表3區段勘查表」。兩種都要能吃：
前者依名稱取區段編號，後者從格子 `G3`（區段編號欄）讀。

## 4. 輸出

**統一的勘查事實格式**，與 `kernel/fixtures/shulin_survey_facts.json` 的
`segments` 區塊同一個 schema。這是三種輸入格式共用的中間層，下游
（`kernel` 計算、`xlsxform` 回填）完全不必知道資料是從哪種檔案讀來的。

```
{
  "segments": {
    "P001-00": {
      "source": {"file": "...", "sheet": "表3 P001-00"},
      "segment_range": "...",
      "raw":   {factor_id: 勘查表上寫的原值},
      "facts": {factor_id: 計算用的值}
    }
  }
}
```

`raw` 與 `facts` 分開的理由見第 5 節。

## 5. `raw` 與 `facts` 為什麼要分開

因為存在「勘查表上寫的」與「計算要用的」不一致的情況，而兩者都必須保留。

本案的實例是容積率。地價查估單位口頭指示「比較標的跟比準地的道路如果沒有到達
八米，容積就不能到達 200 以上，這個專案內都是八米內，所以容積一律使用 200
計算」。勘查表原載 P001-00、P003-00、P004-00 為 260%，P002-00 為 200%。

處理方式：

- `raw` 保留 260%（勘查表是現場記錄，要忠實）
- `facts` 一律 200%（計算依局處指示）
- 兩者的差異由一份可宣告的 **`case_overrides`** 說明，含理由

這條規則不能寫進 `xlsxform/read.py`（那只負責讀），也不能寫進 `kernel/`
（那是規則引擎，不認識個案特例）。它是案件層級的設定，必須是資料而不是程式碼，
而且要能追溯到誰說的、為什麼。

## 6. 型別轉換

Excel 格子讀出來的型別與 `kernel` 需要的不一致，reader 要負責轉換。

| 欄位類型 | xlsx 裡的樣子 | 轉成 | 舉例 |
| --- | --- | --- | --- |
| 百分比 | 字串 `"50%"` 或數值 `0.5` | 數值 50 | 建蔽率、容積率 |
| 長度 | 數值 | 原樣 | 主要道路寬度 28 |
| 類別 | 字串 | 原樣去空白 | 日照「充分」 |
| 改良項數 | 勾選文字 | 數值（■ 的個數） | 土地改良 4 |
| 未勾選 | 空白、`○`、`-` | `None` | 13 個圈選類細項 |

哪些欄位是百分比，由 `layout.py` 宣告，寫入與讀取共用同一份清單，避免兩邊
不同步。

## 7. 驗收標準

### 7.1 Round-trip

讀回 `xlsxform` 自己產出的表3 xlsx，除了 `case_overrides` 那一項之外，
四個區段的 `facts` 必須與 `kernel/fixtures/shulin_survey_facts.json` 完全一致。

這是最強的一條，因為它把「寫入」與「讀取」綁在同一份格位對映上，任一邊改壞
另一邊就會發現。

### 7.2 端到端一致

`--from-xlsx` 與 `--facts` 兩種來源跑同一條鏈，產出的數字必須相同：

```
表5-1  總修正數 +23.50% / +14.75% / +14.75%
表4    試算價格 170,337 / 161,577 / 206,885 元/㎡
       比準地比較價格 176,921、比準地地價 177,000 元/㎡
```

### 7.3 其他

1. 讀不出來要明確報錯，不可安靜跳過。缺工作表、缺區段編號、細項讀不到值
   都要能區分。
2. 未勾選（`None`）與讀取失敗必須分得開。前者是事實（沒有那個設施），
   後者是問題。
3. `case_overrides` 套用後，`raw` 仍保留原值。
4. 完整測試維持 252 passed 以上。

## 8. 刻意不做

1. **不讀表5-1 與表4 的 xlsx。** 那兩張是我們要產出的，不是輸入。之後若要做
   「審查別人填好的表5-1」才需要，那是另一條路。
2. **不做 xlsx 的版面自動偵測。** 格位對映仍是人工量測的常數。換一份範本要重新
   量，這一點與 PDF 相同，只是 xlsx 的格位比座標穩定得多。
3. **不碰 `parser/`。** PDF 那條路維持現狀（對金山範本可用，對新版面明確報錯）。
4. **不做 OCR。**

## 9. 對「泛用性」這個說法的影響

做完之後可以誠實地講：換行政區或用地類別只要換一份 JSON 規則集，程式碼不動
（已用四組規則集驗證：金山商業、樹林住宅、兩組合成的假行政區）；換書表版面
需要重新校準格位對映。

這個區分很重要，不要說成「換任何書表都不必改」。
